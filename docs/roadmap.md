  - **`cache.*` model (shipped):** value expressions reference raw cached values as `cache.<provider>.<field>`, distinct from `<provider>.<field>` (the resolved field). - [ ] **`fseventsd` memory growth from comb's long-lived FSEvents client (suspected leak).** Surfaced 2026-06-15 while investigating a "comb lags ~5s catching up after `git checkout`" report. Live forensics (tmux-bridge; `sample`/`footprint`/`vmmap` on the machine) found the OS daemon `fseventsd` bloated to **2.0 GB resident** — almost entirely heap event-*retention* (DefaultMallocZone 1.6 GB / 7.8M allocs + **PathStringZone 471 MB / ~2.5M path strings**), NOT the on-disk `.fseventsd` store (only 59 MB) — and delivering events with **~5s latency**, which is the actual cause of the lag (the comb daemon is blocked on the OS handing it the event, not on comb's own refresh). Two contributors: (1) **71 leaked test daemons** on unique temp sockets — `TestDaemon` spawned `comb daemon` and only reaped in `Drop`, which nextest's SIGKILL of timed-out tests skips; **fixed** via opt-in `--exit-with-parent` (commit `f581bc1b`). But they were idle with decayed watches, so likely *not* the pin. (2) **The likely pin: a single long-lived comb daemon** (17-day uptime — the one active FSEvents client in the sample). `fseventsd` retains event history back to each client's last-acknowledged event id, so a client that under-drains / never advances forces unbounded retention. Compounding: vendored `notify`'s `FsEventWatcher` does `stop()`+`run()` — recreating the **entire** FSEventStream — on *every* `.watch()` add (`vendor/notify/src/fsevent.rs:308`), so each watch-path change re-registers the client (matches the repeated `fsevent_add_client` + "Resolve user group list" churn in `fseventsd`'s log). **TODO — audit comb's FSEvents lifecycle:** (a) repro — leave one daemon watching a busy tree for hours/days and watch `footprint fseventsd` for unbounded growth; (b) reduce stream re-creation — batch/coalesce watch registrations instead of one `stop()`/`run()` per added path; (c) confirm the scheduler always drains `fs_rx` promptly so `fseventsd` can release history; (d) consider capping watched-path count or periodically recycling the watcher. Restarting `fseventsd` clears it but it may recur.
